# 02｜架构逻辑：GitHub 母仓 + 阿里云运行层

> 随行案的核心不是把所有东西放在一个平台里，而是把核心能力资产与运行交付设施分层。

---

## 1. 总体架构

随行案采用双层架构：

```text
GitHub 母仓
  ↓
沉淀核心方法、工作流、模板、回流规则、版本记录

阿里云运行层
  ↓
承载服务器、数据库、网页、API、安全防护、企业部署
```

一句话：

> **GitHub 保核心，阿里云做运行。**

---

## 2. GitHub 母仓承载什么

GitHub 不只是代码仓库，而是随行案的核心架构资产库。

它适合承载：

- 产品方法论；
- 70 / 20 / 10 方案设计模型；
- 方案草案工作流；
- 需求—数据—方案模块绑定逻辑；
- 模板体系；
- 回流复盘机制；
- 版本迭代记录；
- 参赛文档；
- 展示仓叙事；
- 企业版架构说明。

GitHub 的作用是：

> **让随行案的核心能力不依赖某一个服务器、平台或模型。**

服务器可以更换，数据库可以迁移，大模型 API 可以切换，但核心工作流和架构逻辑可以持续沉淀。

---

## 3. 阿里云运行层承载什么

阿里云负责让随行案真正跑起来、交付出去、部署到客户侧。

它适合承载：

- ECS 服务器；
- 数据库；
- 前端网页；
- 后端接口；
- API / 大模型调用；
- 用户系统；
- 文件存储；
- 企业私有化部署；
- 安全防护；
- 防火墙；
- 备份与运维；
- 平台合作与生态推广。

阿里云的作用是：

> **把 GitHub 中沉淀的核心架构变成用户可以访问、企业可以使用、平台可以推广的产品。**

---

## 4. 这个分层的价值

### 4.1 保留核心控制权

如果核心模型、模板、回流逻辑和商业方法全部锁在运行平台里，产品会变得被动。

随行案的逻辑是：

> 核心架构在 GitHub，运行设施在阿里云。

这意味着可以借平台资源，但不把产品命脉完全交给平台。

### 4.2 便于参赛与合作背书

展示仓可以证明随行案不是一个临时 Demo，而是一套有版本记录、有方法论、有架构文档、有迭代路径的 AI 工作流产品模型。

对赛事评审、平台合作方、企业客户来说，这比单纯展示一个网页更容易建立信任。

### 4.3 便于版本升级

个人版、VIP版和企业版可以共用同一套母仓能力，再在不同交付层做差异化。

```text
母仓：通用方法论 + 基础流程 + 模板规则
  ├─ 个人版：调用通用模板，快速生成方案草案
  ├─ VIP版：沉淀私人模板库、私人方案仓库和回流记录
  └─ 企业版：定制企业流程、权限、内控、数据隔离和组织资产库
```

### 4.4 便于未来开源或半开源

成熟后，可以选择开放部分社区版、基础模板层或展示层；同时保留企业内控、权限、客户数据绑定、私有部署、行业定制等商业能力。

这条路线类似：

> **开源建立信任，闭源保留商业深度。**

---

## 5. 母仓 / 子仓模式

随行案未来可以形成：

> **母仓 + 用户子仓 + 企业子仓。**

| 仓库层级 | 作用 |
|---|---|
| **母仓** | 保存通用方法论、核心流程、基础模板、回流机制和版本记录 |
| **VIP 子仓** | 保存个人用户的方案模板、历史方案、客户需求、回流记录 |
| **企业子仓** | 保存企业客户的内部流程、审批规则、客户数据、权限结构、成功案例 |

这形成一个重要商业结构：

> **母仓是产品核心，子仓是客户资产。**

用户越用，子仓越有价值；企业越用，组织方案资产越厚。

---

## 6. 与 Dify / DeepSeek 路径的关系

随行案参考的是一种已经被市场验证过的 AI 产品路径：

> 先用 GitHub 沉淀核心架构，再用云平台完成运行、部署、交付和商业化。

Dify 更接近“GitHub 开源核心 + 云端商业化 + 企业服务”的应用软件路径；DeepSeek 更接近“开放模型能力带来生态势能”的技术路径。

随行案不照搬它们，而是吸收其中的架构思想：

> **核心资产可版本化、可展示、可协作；运行设施可部署、可扩展、可商业化。**

---

## 7. 最终架构逻辑

随行案的架构逻辑价值不是做一个 AI 写方案工具，而是：

> **把方案设计能力从个人灵感和临时文档中抽离出来，沉淀为可运行、可复用、可回流、可商业化交付的系统资产。**

最短表达：

> **GitHub 保核心，阿里云做放大；母仓保方法，子仓沉淀客户资产。**
